# Duo — Phase 1: Foundation Design

**Date:** 2026-09-13
**Status:** Approved
**Stack:** Next.js 16 (App Router, TypeScript) · Neon Postgres · Drizzle ORM · Better Auth · Tailwind CSS + shadcn/ui · SMTP (nodemailer) · Vercel

## Product context

Duo ("Our Little World") is a private, cute digital home for two people. The core loop is
**Discover → Match → Plan → Do → Save Memory**. The MVP is built in phases; this spec covers
Phase 1 only.

| Phase | Scope |
|-------|-------|
| **1. Foundation** (this spec) | Infra, auth, couple pairing, minimal home with "together for N days" |
| 2. Our Plans | Shared plans: type, what/when/where/budget, status 💭 Idea → 📌 Planned → ❤️ Done |
| 3. Discover & Match | Both partners swipe activity ideas independently; mutual ❤️ = match → add to plans |
| 4. Memories | Completed plans become memories (photos, place, note) on a timeline |
| 5. Pet & streaks | Shared pet (e.g. Momo) gains XP from couple actions; relationship streak |

Out of MVP: Couple Wallet, Daily mood check-in, push notifications.

## Goals

- Two people can sign up (magic link or Google), pair via an invite link, and both land on a
  shared home screen showing their names and days together.
- The app is multi-tenant: any number of couples, every couple's data isolated.
- The foundation (schema conventions, auth guards, design tokens, deploy pipeline) is ready for
  Phases 2–5 to build on without rework.

## Non-goals (Phase 1)

- Unpairing / leaving a couple, deleting accounts
- Editing profile or `together_since` after onboarding
- Push notifications, realtime sync
- Any Phase 2–5 feature

## Architecture

- **Rendering:** React Server Components for pages; Server Actions for all mutations. No
  separate REST API except Better Auth's handler at `/api/auth/[...all]`.
- **Authorization:** `proxy.ts` (Next.js 16's replacement for `middleware.ts`) only performs an
  optimistic redirect to `/sign-in` when no session cookie exists. The real checks happen
  server-side in a data-access layer:
  - `requireUser()` — returns the session user or redirects to `/sign-in`.
  - `requireCouple()` — calls `requireUser()`, returns `{ user, couple, members }` or redirects
    to `/onboarding` if the user has no couple.
  - Every couple-scoped query takes `coupleId` from `requireCouple()`, never from client input.
- **Database driver:** `drizzle-orm/neon-serverless` with a `Pool` (WebSocket), because the
  join-couple operation needs an interactive transaction with row locking, which the Neon HTTP
  driver does not support.

## Data model

All app tables use `text` ids generated with `crypto.randomUUID()` and `timestamptz` timestamps
defaulting to `now()`.

**Better Auth tables** (generated by Better Auth CLI for the Drizzle adapter): `user`,
`session`, `account`, `verification`. `user.name` is set during onboarding.

**`couples`**
| column | type | notes |
|--------|------|-------|
| id | text PK | |
| together_since | date NOT NULL | the date they got together |
| created_at | timestamptz NOT NULL | |

**`couple_members`**
| column | type | notes |
|--------|------|-------|
| couple_id | text FK → couples.id, ON DELETE CASCADE | |
| user_id | text FK → user.id, ON DELETE CASCADE, UNIQUE | a user belongs to at most one couple |
| joined_at | timestamptz NOT NULL | |
| | PK (couple_id, user_id) | |

A couple has at most 2 members, enforced inside `acceptInvite`'s transaction.

**`couple_invites`**
| column | type | notes |
|--------|------|-------|
| id | text PK | |
| couple_id | text FK → couples.id, ON DELETE CASCADE | |
| created_by | text FK → user.id | |
| token | text NOT NULL UNIQUE | random invite token |
| expires_at | timestamptz NOT NULL | created_at + 7 days |
| used_at | timestamptz NULL | |
| revoked_at | timestamptz NULL | set when a newer invite is created |
| created_at | timestamptz NOT NULL | |

Token: 32 random bytes, base64url-encoded; invite URL is `{BETTER_AUTH_URL}/invite/{token}`.
The token is stored in plaintext so the waiting screen can always re-display the link. This is
an accepted trade-off: a token only lets someone join a couple that has one member, is
single-use, expires in 7 days, and the inviter sees who joined.

## Flows

### Sign in
1. `/sign-in` offers "Continue with Google" and an email field for a magic link.
2. Magic link: Better Auth `magicLink` plugin; email sent via SMTP; link valid 15 minutes.
   After submitting, the user sees `/check-email`.
3. Both methods accept a `callbackURL` so an invitee returns to `/invite/[token]` after signing in.
4. After sign-in without a callback, `/` routes: no couple → `/onboarding`; has couple → `/home`.

### Onboarding (creating a couple)
1. `/onboarding` requires a user without a couple (users with a couple are redirected to `/home`).
2. Form: "What should we call you?" (1–40 chars, trimmed) and "When did you two get together?"
   (a date, not in the future).
3. Server Action `createCouple` in one transaction: update `user.name`, insert `couples`, insert
   `couple_members` for the user, create an invite. Redirect to `/home`.

### Home — waiting state (1 member)
- "Waiting for your person 💌" with the invite link, a Share button (Web Share API, falling back
  to copy-to-clipboard) and "Make a new link" (revokes the old invite, creates a new one).
- The page shows the couple's active invite (not used, not revoked, not expired). If none exists
  (e.g. it expired), the page shows only a "Make a new link" button; pressing it creates one.

### Accepting an invite
`/invite/[token]`:
1. Not signed in → sign-in screen with `callbackURL=/invite/[token]`, showing the inviter's name.
2. Signed in → look up invite by token and render one of:
   | condition | screen |
   |-----------|--------|
   | no such invite, or revoked | "This link doesn't work anymore — ask for a new one" |
   | expired | same as above, mentioning expiry |
   | used | "This link was already used" |
   | invite created by current user | "This is your own invite — send it to your partner" |
   | current user's couple already has a partner | "You're already paired" + link to home |
   | couple already has 2 members | "This couple is already complete" |
   | valid | "{inviter} invited you to Duo 💕" + "What should we call you?" (prefilled with the user's name, e.g. from Google) + Accept button |

   A user alone in their own couple can accept: their solo couple is removed in the same transaction.
3. Server Action `acceptInvite(token, { userId, name })` (name validated with the same 1–40 char rule), one transaction:
   - look up the invite by token and the user's current couple, then lock both couples in id order in
     one statement: `SELECT id FROM couples WHERE id IN (invite.couple_id, current couple) ORDER BY id FOR UPDATE`
   - re-read the invite and re-check every condition above (the page render check is not trusted)
   - if the user is alone in a different couple, delete that couple (cascades to its membership and invites)
   - insert `couple_members`, set `invite.used_at = now()`, set `user.name`
   - on unique-violation of `couple_members.user_id` (race), return "already paired"
   - redirect to `/home`

`acceptInvite` returns a typed result (`{ ok: true } | { ok: false, reason }`) so the page and the
action share one set of reason codes and messages.

### Home — paired state (2 members)
- Hero: **{nameA} ❤️ {nameB}**, "together for **N** days".
- `daysTogether` = whole days between `together_since` and today in the viewer's timezone
  (read from a `tz` cookie set client-side from `Intl.DateTimeFormat().resolvedOptions().timeZone`,
  falling back to UTC). Day 0 is shown as "your first day together".
- Phase 1 home shows only the hero and a sign-out control. No placeholder cards for later
  phases ("Next plan", "Today's little thing").

## Visual system

- Background off-white `#FBF8F3`, text near-black `#1F1B16`, pastel accents (peach `#FFD8C2`,
  lilac `#E3DAFF`, mint `#CFF0DE`, butter `#FFF1B8`).
- Cards `rounded-3xl`, soft shadows, generous whitespace; large display type for the hero.
- Fonts via `next/font/google`: Bricolage Grotesque for display, Inter for body.
- Tokens defined as CSS variables in `globals.css` and mapped into Tailwind + shadcn theme.
- Mobile-first; content max width ~480px centered on desktop.
- Light mode only in Phase 1.
- PWA: `app/manifest.ts` with name "Duo", theme color, icons; no service worker in Phase 1.

## Deployment

- Vercel project connected to the Git repo; Neon via the Vercel Marketplace integration, which
  creates a Neon branch per preview deployment and injects `DATABASE_URL`.
- Migrations: `drizzle-kit generate` locally, committed to `drizzle/`; applied with
  `drizzle-kit migrate` as part of the Vercel build command (`drizzle-kit migrate && next build`).
- Environment variables:
  `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID`,
  `GOOGLE_CLIENT_SECRET`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`,
  `SMTP_SECURE`, `EMAIL_FROM`.
- Google OAuth redirect URIs: `http://localhost:3000/api/auth/callback/google` and the production
  domain. Preview deployments use magic link only (Google rejects wildcard redirect URIs).

## Error handling

- Server Actions validate input with Zod and return typed errors rendered inline on forms.
- Invite and pairing failures map to the reason codes above; never a raw 500.
- SMTP failures on magic-link send show "We couldn't send the email, try again".
- Unexpected errors fall through to a cute `app/error.tsx` boundary; `app/not-found.tsx` likewise.

## Testing

- **Vitest (unit/integration)** against a real Postgres (a Neon test branch via
  `TEST_DATABASE_URL`), truncating app tables between tests:
  - `createCouple`: creates couple, member, invite; rejects user already in a couple; rejects
    future dates.
  - `acceptInvite`: success; expired; used; revoked; own invite; already paired; couple full;
    two users accepting the same invite concurrently → exactly one succeeds; one user accepting
    invites to two different couples concurrently → exactly one succeeds.
  - Creating a new invite revokes the previous one.
  - `daysTogether`: timezone boundary cases, day 0.
- **Playwright (e2e):** user A signs in via magic link (test mode captures the link instead of
  sending over SMTP), onboards, copies invite; user B opens it in a second browser context,
  signs in, accepts; both see "A ❤️ B · together for N days".
- Test email transport: when `EMAIL_TRANSPORT=file`, `email.ts` writes each magic link to
  `.e2e-mail/<email>.txt` instead of sending over SMTP; Playwright reads the link from there.
  Production always sends over SMTP.
